extending the sales visit planning platform with kubernetes and istio.
same four services from ca1, now deployed into a kubernetes cluster with a service mesh.
local deployment target is KinD or Minikube.
helm is used to start the full stack with a single command for assessment.
====
stack
kubernetes for container orchestration.
istio for the service mesh.
helm for packaging and deployment.
envoy proxies (injected by istio) for all inter-service traffic control.
prometheus + grafana for metrics.
jaeger for distributed tracing.
kiali for cluster topology visualisation.
====
workload types
stateless deployments:
- customer_user_service
- planning_service
- expense_service
- frontend_service

stateful sets:
- customer_user_db (postgresql)
- planning_db (postgresql)
- expense_db (postgresql)
- redis
- kafka
- zookeeper (kafka dependency)

each statefulset gets a persistent volume claim.
====
networking
nginx is replaced by an istio ingress gateway.
the gateway handles all external traffic on port 80.
path-based routing to services mirrors the existing nginx.conf rules.
internal service-to-service traffic goes through the istio mesh (envoy sidecars).
====
istio features to implement
secure communications:
mtls enabled in strict mode across the mesh.
peer authentication policy applied at namespace level.
authorisation policies lock down which services can talk to which.
only intended workloads can reach a given service (zero trust).

traffic control:
load balancing configured via destination rules.
canary deployment targeting the planning service.
canary splits traffic between a stable release and a new release using virtual services.
start at 90/10 and demonstrate shifting to 50/50.

observability:
prometheus scrapes metrics from all envoy sidecars.
grafana dashboards show request rate, error rate, and latency per service.
jaeger traces the full request path across services.
kiali renders the live cluster topology and traffic flow.
tracing headers must be propagated through the fastapi services.

resilience:
rate limiting applied via envoy local rate limit filter on the planning service.
circuit breaker configured via outlier detection in destination rules.
target the maps service integration as the circuit breaker candidate.

fault and chaos testing:
istio fault injection used to simulate latency and errors.
inject a 3 second delay on the customer_user_service.
inject a 500 error on the expense_service at a set percentage.
observe impact through grafana and jaeger.
document the results.
====
helm chart structure
one chart at the project root.
templates/ contains all kubernetes manifests.
values.yaml holds environment-specific config (image tags, replica counts, resource limits).
secrets managed via kubernetes secret objects, not committed to the repo.
configmaps for non-sensitive environment variables.
a single helm install command brings up the full stack.
====
kafka in kubernetes
kafka and zookeeper run as statefulsets.
kafka bootstrap server env var updated in all service deployments to point to the in-cluster kafka service name.
istio does not proxy kafka tcp traffic at l7 by default.
serviceentry and destinationrule added for kafka to handle tcp load balancing.
====
database migrations
alembic migrations run as kubernetes jobs on startup, one per service.
each job runs before the service deployment becomes available using init containers or a separate job with a dependency.
====
build order
step 1 - write kubernetes manifests
start with the four application services as deployments.
add statefulsets for each postgresql db, redis, kafka, and zookeeper.
add persistent volume claims.
add services (clusterip for internal, the gateway handles external).
test with kubectl apply before touching helm or istio.

step 2 - wrap in helm
move all manifests into a helm chart under templates/.
extract variables into values.yaml.
verify helm install brings the stack up cleanly from scratch.

step 3 - install istio and verify injection
install istio into the cluster using istioctl.
label the namespace for sidecar injection.
confirm envoy proxies are running as sidecars in all application pods.
confirm traffic still flows correctly before configuring anything.

step 4 - mtls and authorisation policies
enable peer authentication in strict mtls mode.
write authorisation policies for each service.
planning_service can only be reached by frontend_service and kafka.
customer_user_service can only be reached by planning_service and frontend_service.
expense_service can only be reached by frontend_service.
test that unauthorised traffic is rejected.

step 5 - observability
deploy prometheus, grafana, jaeger, and kiali using the istio addons.
add tracing header propagation to the fastapi services (x-b3 headers).
generate traffic and confirm traces appear in jaeger end to end.
confirm kiali shows the correct service graph.
set up grafana dashboards for the four services.

step 6 - traffic control
configure destination rules for load balancing on the planning and expense services.
create a v2 image of the planning service with a visible change (a version header or log line).
write a virtual service to split traffic 90/10 between v1 and v2.
demonstrate shifting the split.

step 7 - resilience
add local rate limit filter to the planning service ingress.
configure outlier detection on the customer_user_service destination rule as the circuit breaker.
test that the rate limit triggers under load.
test that the circuit breaker opens when errors exceed the threshold.

step 8 - fault and chaos testing
inject a fixed delay on the customer_user_service using an istio virtual service fault.
inject an abort fault on the expense_service at 30 percent of requests.
run the test suite and record results.
capture grafana screenshots showing latency spike and error rate increase.
capture jaeger traces showing the delay propagating.
document what broke, what held, and what the circuit breaker did.

step 9 - report
covers istio architecture overview.
explains how envoy controls traffic within the mesh.
describes how the security model works in this project specifically.
compares sidecar vs ambient istio with pros and cons.
explains l4 vs l7 and how l7 is addressed in ambient mode.
includes screenshots of kiali, grafana, and jaeger from the live cluster.
includes test results from the fault injection step.
